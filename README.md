# Job Application Tracker

A private, single-user application for saving job descriptions, PDF snapshots, statuses, and application notes. It runs locally with Express, EJS, SQLite, and Puppeteer; there is no authentication or external service.

## Requirements

- Node.js 20 or newer
- npm
- Enough disk space for Chromium (downloaded by Puppeteer during installation) and saved snapshots

On minimal Linux installations, Chromium may also need system libraries. See the official [Puppeteer troubleshooting guide](https://pptr.dev/troubleshooting) for the current package list for your distribution. Windows and macOS normally need no extra browser prerequisites.

## Install and run

```sh
npm install
npm start
```

Open <http://localhost:3000>. On first start, the app creates:

- `data/applications.sqlite` for the database
- `storage/` for generated PDFs and uploaded snapshots

Both locations are intentionally outside the public static directory and ignored by Git.

For development with automatic server restarts:

```sh
npm run dev
```

## Tests

```sh
npm test
```

The test suite uses an in-memory database and a fake capture service, so it does not launch Chromium.

## Configuration

Optional environment variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `3000` | HTTP port |
| `DATABASE_PATH` | `./data/applications.sqlite` | SQLite database file |
| `STORAGE_DIR` | `./storage` | Private snapshot directory |

Use absolute paths for `DATABASE_PATH` and `STORAGE_DIR` when placing data outside this project.

## How capture failures work

When a URL is submitted, Puppeteer attempts to load the page, read its title, and print it to PDF. Some job sites block automated browsers, require authentication, or time out. In that case the app keeps the URL visible and presents a recovery form. Supply or edit the job name and upload a PDF, PNG, JPEG, GIF, or WebP snapshot (maximum 10 MB) to finish saving the application.

## Data and file safety

- SQLite foreign keys are enabled by the schema connection.
- SQL values use parameterized queries.
- Uploaded filenames are never used as storage paths; the app generates UUID-based names.
- Snapshots are served only through `/files/:id` after a database lookup and path check.
- Replacing a snapshot first saves the new file and commits the database update, then removes the old file.
